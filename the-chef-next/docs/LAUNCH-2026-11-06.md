## 4. Payment rail (launch)

**REPORTED:** Chef uses Clover as his main processor (and Business Zelle
sometimes); 50% locks the date and the balance is due the morning of the event.

Launch procedure (no website checkout, so no fake payment success is possible):

1. A request arrives in `/crm/leads` with the dishes, date, guests and location.
2. Chef reviews, adjusts the menu with the customer, and creates the quote in Clover.
3. Chef sends a **Clover invoice** for the deposit, then sets the stage to **Awaiting Deposit**.
4. Chef sets the stage to **Booked** only after Clover shows the deposit as
   paid. Never from a screenshot or a redirect.
5. The balance is collected per the approved policy, tracked in Clover.

Stripe stays deferred. The uncommitted Phase 3 work can be vetted separately,
but only on Chef's own Stripe account, in test mode first, with signed webhooks,
and with live mode separately approved. **BLOCKED:** owner approval of the rail
and of the public deposit/cancellation wording (`DEPOSIT_POLICY_APPROVED = false`).

New findings from the re-check (both predate today's fixes; **fixed in `9dd1e75`, see below**):
- **F-5:** issuing a proposal always resets its expiry to 14 days from
  issue (`issueProposal` → `prepare_and_issue_proposal`). An Expires value
  typed in the quote settings is saved correctly in ET, but is replaced on
  issue.
- **F-6:** the CRM's **Approve / Cancel** buttons for scheduled actions fail
  with "Could not save" (`?error=validation`).
  - The captured request carries only the action ID. The clicked button's
    `approved` value never reaches the server action, although the browser
    reports the button as the submitter.
  - The automation rules' Enable/Disable buttons use the same pattern and
    were not clicked.
  - No launch impact while automations stay unused (no email provider), but
    operators can't approve or cancel follow-ups in the UI.
  - Likely fix: a hidden input per form instead of the button's name/value.

Fixes for F-5 and F-6 (`9dd1e75`, app-only, no migration; local tests pass,
**not yet pushed or re-verified on hosted**):
- **F-5:** issuing now keeps the saved Expires date for the version and the
  client link. It falls back to 14 days only when no date is saved, and
  refuses a date that has already passed with a clear message. The issue
  panel shows the expiry that will be used.
- **F-6 root cause:** these forms have a hidden `<input name="id">`, which
  makes `form.id` return that element. React adds the clicked button's value
  through a temporary input tied to `form.id`, so the value is dropped. This
  was reproduced locally in a clean browser. The decision now travels in a
  hidden input. The client proposal page and the Stripe link buttons have no
  `id` field and were never affected.
- New regression tests: `proposal-expiry`, and `form-submitter`, which scans
  every form for this pattern.
