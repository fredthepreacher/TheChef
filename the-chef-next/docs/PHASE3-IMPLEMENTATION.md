# Phase 3 — Catering Revenue Operations Implementation Plan

## Starting point

Phase 3 starts from approved commit `2164ce326d9658c17dcb07cebc96543ce40448aa` on branch `feat/catering-crm-revenue-ops`.

The application remains Next.js 15.5.25 App Router with React 18, TypeScript, Server Components and Server Actions. Supabase provides Auth, PostgreSQL, RLS, private Storage, and the atomic Catering intake. The CRM is protected under `/crm/**`; the public Catering intake is `/catering/inquiry`; the Entertainment/Music experience has no CRM relationship and will remain unchanged.

Phase 2 already provides clients, leads, catering events, reusable venues, event menu revisions, event documents, tasks, readiness, communications, an immutable activity log, and `crm_private.email_outbox`. The framework and dependency baseline remains frozen unless an approved provider requires one narrowly scoped SDK.

Stripe, Resend, and Vercel AI SDK dependencies are now installed and implemented behind server-only configuration boundaries. The required variable names are documented in `.env.example`; no real credential is committed. Vercel Preview still lacks the Phase 3 provider variables, so provider acceptance remains gated. The `OPENAI_API_KEY` reference in `supabase/config.toml` is an untouched Supabase template placeholder, not a configured integration.

## Commercial state model

Operational event state and financial booking state will remain distinct:

- `events.status` continues to describe operations: Prospective, Booked, Pre Event, Completed, Cancelled, or Archived.
- A new commercial state describes the sales/financial path: Prospective, Quoted, Awaiting Approval, Approved Deposit Pending, Booked, Completed, or Cancelled.
- Quote approval never records payment.
- An event cannot enter the commercial Booked state while a required deposit remains unpaid.
- The operational Booked action will use the same server-controlled eligibility check so the two states cannot contradict each other.

All money will use integer cents and all percentage rates will use integer basis points. Browser-supplied subtotals, taxes, totals, amount paid, and remaining balance will never be trusted.

## Proposed database additions

One primary Phase 3 migration adds the normalized revenue model. The additive hardening migration `20261108165321_phase3_revenue_hardening.sql` corrects issues found during local acceptance without rewriting the already-hosted primary migration. Further migrations are limited to hosted advisor or acceptance findings and must be created with the installed Supabase CLI before SQL is written.

### Quotes and immutable revisions

`quotes` will identify a quote across revisions and store:

- Stable human-readable quote number generated by the database.
- Client and catering event.
- Current revision pointer.
- Overall lifecycle state and created/updated timestamps.

`quote_versions` will store each commercial snapshot:

- Revision number, created date, expiry, and state.
- Internal notes separated from client-facing notes.
- Currency.
- Discount configuration, tax rate, service charge, delivery/travel fee, and optional explicitly enabled gratuity.
- Deposit rule and deposit due date.
- Server-calculated subtotal, discount, taxable amount, tax, charges, gratuity, deposit amount, and final total.
- Ready/sent/viewed/approved/declined/expired/superseded timestamps.
- Approval source and actor metadata.

`quote_line_items` will belong to one quote revision and store description, quantity in a fixed decimal scale, unit price in cents, display order, taxability, and the server-calculated line total.

Draft revisions may be edited. Once a revision is Ready for Review or Sent, its financial and client-facing snapshot becomes immutable. Revising it copies the snapshot and line items into a new Draft revision, marks the prior sent revision Superseded when appropriate, and updates the current revision pointer in one transaction. Historical versions are never overwritten.

Database functions/triggers will:

- Validate state transitions.
- Recalculate all totals with defined rounding.
- Prevent negative or overflow values.
- Enforce one current revision per quote.
- Prevent client-visible publication of internal notes.
- Prevent approval of an expired, revoked, superseded, or draft revision.

### Proposal access

`proposal_access_tokens` will remain private and service-only. It will store a SHA-256 hash of a 256-bit random opaque token, quote revision, expiry, revocation and last-access timestamps. Plaintext tokens will never be stored after link creation.

Public proposal routes will use `/proposal/[token]`, carry `noindex` metadata, and execute only on the server. The server will hash the presented token and query a restricted private function with the Supabase server key. No quote, line-item, agreement, token, or payment table will be granted to `anon`.

The public response will be an explicit sanitized projection containing only client-safe event, menu, pricing, expiry, and acceptance data. Internal notes, CRM activity, operator identity, provider references, private document paths, and database keys remain excluded.

Proposal views and actions will be rate limited. Access events will record the proposal token record, action, timestamp, and a privacy-preserving network fingerprint rather than the raw token or raw IP. Tokens can expire or be revoked immediately.

### Payment requirements and ledger

`event_financials` will store the active approved quote relationship and server-derived contract requirements:

- Contract value.
- Required deposit and due date.
- Final balance due date.
- Internal payment notes.
- Commercial booking/payment state.

`payment_transactions` will be an append-oriented ledger:

- Event, quote revision, amount in cents and currency.
- Transaction kind: Payment, Refund, or Adjustment.
- Source: verified provider event or authenticated manual operator entry.
- Method label and provider reference.
- Provider event ID/idempotency key.
- Effective timestamp, recorded-by operator, notes, and created timestamp.

Posted provider transactions will be immutable. Corrections use compensating ledger entries rather than rewriting history. Unique provider event IDs and idempotency keys prevent duplicate credit.

A database function/view will deterministically calculate gross paid, refunded, net collected, remaining balance, deposit satisfaction, overdue state, and the display payment status. “Paid” can only result from verified provider events or an authenticated manual entry. No raw card number, CVV, bank credential, or payment secret enters Supabase.

### Agreements

`agreements` and `agreement_versions` will provide a limited acceptance foundation:

- Quote and event relationship.
- Draft, Sent, Viewed, Accepted, Declined, or Superseded state.
- Immutable agreement text/snapshot and version.
- Sent, viewed, accepted, declined, and superseded timestamps.
- Accepted-by typed name and explicit consent statement.
- Associated proposal token and uploaded signed-contract document when applicable.
- Privacy-preserving network fingerprint and a bounded user-agent snapshot for an audit record.

This is click acceptance and evidence capture, not a representation that the application is a regulated or legally equivalent electronic-signature platform. A third-party e-signature integration remains separate unless the owner later selects one with legal counsel.

### Communications, delivery attempts, and automations

The existing `communications` and `crm_private.email_outbox` remain the source of truth. Phase 3 will add:

- `email_delivery_attempts` in the private schema for attempt number, provider, request idempotency key, provider message ID, safe error category, response time, and outcome.
- Additional communication states for provider acceptance, delivery, bounce, complaint, and suppression where supported.
- `automation_rules` for event type, delay, enabled state, approval requirement, and template key.
- `scheduled_actions` for due time, lifecycle state, cancellation, idempotency key, source entity, and resulting communication/action.

Lifecycle transitions will schedule deterministic actions. Re-running the scheduler cannot duplicate them. Cancelling or changing the source state cancels no-longer-valid pending actions. Pricing, negotiation, quote, contract, and rebooking content requires operator approval before enqueueing. Inquiry acknowledgment and explicitly approved fixed operational templates may be eligible for automatic delivery.

A protected server endpoint will claim due work with database locking, process bounded batches, and record results. Preview acceptance will invoke it manually. Production scheduling will not be enabled or connected to a production domain during this phase.

## Quote and proposal UI

### CRM routes

- `/crm/quotes` — quote pipeline and filters.
- `/crm/quotes/new` — create a quote for an existing client/event.
- `/crm/quotes/[id]` — revision history, line-item editor, totals, review, send controls, approval state, and audit history.
- `/crm/payments` — deposits, balances, overdue items, and recent payments.
- `/crm/events/[id]` — commercial summary, approved quote, payment ledger, agreement, and next action alongside existing operations.
- `/crm/communications` — queued, approval-required, failed, and delivered messages.

### Client route

- `/proposal/[token]` — branded, mobile-friendly, server-rendered proposal.

The proposal will show event details, selected menu/package, line items, totals, deposit terms, expiry, agreement snapshot, and explicit Approve, Decline, or Request Revision actions. It will never expose internal notes. The payment action remains unavailable until the payment provider is approved and a server-created hosted checkout session exists.

## Payment-provider architecture and decision

Stripe Checkout is implemented but not credentialed in Preview. It uses server-created hosted Checkout Sessions and signed webhooks, keeping card data off the application and giving each payment a provider reference.

The proposed adapter will expose:

- Create hosted checkout for the exact server-calculated deposit or balance.
- Retrieve provider payment state for reconciliation.
- Verify and normalize webhooks from the raw request body.
- Create refunds only from an explicit authenticated operator action in a later approved scope.

The webhook route will verify Stripe signatures before parsing business data, persist the provider event ID before fulfillment, ignore duplicates, reject amount/currency/entity mismatches, append a ledger entry, and only then update derived commercial state. Visiting success/cancel URLs never marks payment paid.

Current US standard Stripe pricing is no setup fee and no monthly fee, with domestic online cards at 2.9% + $0.30 per successful transaction. Stripe Checkout is included. An optional Stripe-hosted custom checkout domain is $10/month and is unnecessary for this phase. Source: https://stripe.com/pricing and https://stripe.com/payments/checkout.

The owner approved Stripe test mode. Preview test credentials and the signed webhook remain the external setup boundary; live mode remains prohibited.

## Email-delivery architecture and decision

The Resend adapter, dispatcher, and signed webhook are implemented but not credentialed in Preview. Delivery remains gated on a Chef-owned domain/subdomain, approved addresses, DNS verification, and server-only credentials.

The adapter will use the existing outbox idempotency key as the provider idempotency key, persist the provider message ID, and record each attempt. A signed webhook will update Delivered, Bounced, Complained, or Suppressed states without overwriting the original message snapshot.

The first templates will be inquiry acknowledgment, proposal sent, quote follow-up, deposit/booking confirmation, upcoming-event reminder, thank-you, and review request. Real customer email will not be sent during acceptance without an explicit recipient/action approval.

Current Resend transactional pricing is:

- Free: $0/month, 3,000 emails/month, 100/day, three domains, and one webhook endpoint.
- Pro: $20/month, 50,000 emails/month, no daily limit, five webhook endpoints, and $0.90 per additional 1,000 emails when overages are enabled.

Source: https://resend.com/pricing and https://resend.com/docs/knowledge-base/what-is-resend-pricing.

Setup requires a Resend account, a Chef-owned domain or sending subdomain, provider-supplied DKIM/SPF DNS records, a DMARC policy as a deliverability safeguard, an approved From address, an approved Reply-To address, `RESEND_API_KEY` as a server-only Preview variable, and a signed webhook secret. Owner approval is required before adding the SDK or configuring the provider.

## AI boundary and decision

AI will be draft-only and operator initiated. It may summarize a client/event, draft responses and follow-ups, identify missing requirements, and suggest a next administrative action. Every result will be stored as a draft with model, prompt-template version, input entity references, output, token/cost metadata where available, creator, and timestamp.

AI cannot update quote amounts, discounts, contract text, payment/refund state, event booking, COI, or send a message. An operator must explicitly accept or edit any draft before it becomes a communication.

No AI provider is configured. The recommended option is Vercel AI Gateway with the Vercel AI SDK because the application already runs on Vercel and Gateway provides one server-side boundary, spend visibility, and provider/model portability. Current Gateway pricing has zero token markup. Vercel documents a $5 monthly free allowance until a team purchases paid credits; paid use consumes prepaid credits at the selected model's listed token price, and the free allowance ends after moving to paid. Project or API-key budgets can cap spend. Source: https://vercel.com/academy/ai-gateway/ai-gateway-pricing and https://vercel.com/docs/ai-gateway/observability-and-spend/budgets.

The owner approved Vercel AI Gateway with a maximum $5/month project budget. The draft-only operator interface is implemented; model selection, Gateway budget/configuration, and hosted generation acceptance remain gated and secondary to the revenue workflow.

## Security model

- New operator tables receive explicit grants plus RLS using the existing `crm_private.is_operator()` authorization check.
- Private outbox, token, delivery-attempt, provider-event, and rate-limit tables remain in `crm_private` with no browser policy.
- Proposal access uses server-only hashed tokens and a sanitized response, with expiry, revocation, replay/idempotency controls, rate limiting, and `noindex`.
- Sequential IDs and internal UUIDs are not used as client authorization.
- Money and state transitions execute through restricted server/database functions.
- Provider secrets stay in server-only environment variables and are never prefixed `NEXT_PUBLIC_`.
- Webhooks use raw-body signature verification, provider-event uniqueness, amount/currency checks, and audit records.
- No card or bank credentials are collected or stored by the application.
- Agreement snapshots, quote versions, posted ledger rows, and sent communication content are immutable.
- Existing private Storage policies remain unchanged; signed contracts use the existing event-document/version architecture.
- No public registration is added. The CRM stays private and noindex.
- The public Catering and Entertainment/Music experiences stay separate.

Supabase's current Data API guidance requires explicit grants and RLS together. Phase 3 migrations will continue doing both, which also protects the project from the announced change that new tables will stop receiving automatic Data API exposure. References: https://supabase.com/docs/guides/api/securing-your-api and https://supabase.com/changelog.

1. Create a migration with `npx supabase migration new catering_revenue_operations`.
2. Add quote identity, revisions, line items, proposal tokens, financial requirements, ledger, agreements, delivery attempts, automation rules, and scheduled actions.
3. Add checks, unique/idempotency indexes, immutable-state triggers, calculation functions, restricted transition functions, RLS, grants, and audit triggers.
4. Extend events, communications, and the activity timeline without rewriting Phase 1/2 history.
5. Run all migrations in PGlite, then local build/type/lint/tests/audit/secret scans.
6. Apply only the committed migration to `pqfyhkehbwikeaongcdo` after local verification.
7. Run hosted security/performance advisors and add a follow-up migration only when evidence requires it.

No schema is created manually through the Supabase dashboard.

## Testing strategy

### Automated database and domain tests

- Integer-cent quote calculations, rounding, taxability, discounts, fees, gratuity opt-in, deposits, and overflow/negative rejection.
- Draft editing and sent/approved revision immutability.
- Revision copying and supersession.
- Quote transition rules, expiry, decline, and approval idempotency.
- Proposal token entropy shape, hashing, expiry, revocation, wrong-token denial, and sanitized projection.
- Agreement snapshot/version transitions and duplicate-acceptance handling.
- Manual payment authorization, provider event uniqueness, refund/adjustment math, deposit satisfaction, remaining balance, overdue state, and booking guards.
- Email outbox claim/retry/idempotency, delivery attempts, webhook transitions when a provider is approved, and cancellation.
- Automation scheduling, cancellation, due claiming, and duplicate protection.
- AI operator authorization and prohibited-action boundaries if AI is enabled; otherwise provider-not-configured behavior.
- Audit rows and audit-forgery/history-rewrite denial.
- Owner/manager access and staff/inactive/unprovisioned/anonymous denial.
- All Phase 1 and Phase 2 tests continue to execute.

### Hosted acceptance

Use temporary `example.invalid` records and provider test modes only:

1. Create, calculate, review, publish, view, revise, approve, decline, expire, and revoke test quotes.
2. Verify a public proposal token works only while valid and returns no internal fields.
3. Record authenticated manual test payments and verify deterministic booking/payment state.
4. If Stripe is approved, use Stripe test mode and signed test webhooks; never use a real card charge.
5. Test click agreement acceptance while clearly labeling it non-e-signature acceptance.
6. If Resend is approved, use provider-designated test recipients unless the owner explicitly approves an actual recipient.
7. If AI Gateway is approved, exercise draft generation with a strict budget and verify no draft can mutate commercial state or send itself.
8. Verify dashboard totals distinguish Quoted, Approved, Collected, and Outstanding.
9. Re-run CRM desktop/mobile, Catering, Music/Entertainment, Storage, Turnstile, Auth, and RLS regressions.
10. Remove every acceptance row, provider test object, and private Storage artifact.

Phase 3 will not be marked passed for provider delivery, payment processing, agreement acceptance, or AI unless that capability is exercised against the appropriate hosted test service.
